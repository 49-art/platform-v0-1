# Decision log

Every non-trivial decision, with the reason. Nothing is deleted: a changed decision is marked **SUPERSEDED** and a new entry is added. Founder decisions are marked **Travis**. Everything else is a build decision Travis can overturn.

| D-003 | 2026-11-10 | Database: Cloudflare D1. Location is stored as a geohash-5 cell (about 5 km) with its centre in milli-degrees, so distance search is an indexed bounding box. Exact coordinates are never stored. | Travis chose D1. | D-006 | 2026-11-10 | Own auth implementation, not Better Auth. | Spec 11 marks the Better Auth fit [UNVERIFIED]. The acceptance criteria (single-use tokens, same reset response, re-auth windows, sign-out everywhere) are precise, and owning ~400 lines keeps every one of them tested. | Build |
| D-007 | 2026-11-10 | Passwords: Argon2id at the OWASP minimum (m=19 MiB, t=2, p=1) using `@noble/hashes`. Parameters are stored in each hash, so they can be raised and re-hashed on sign-in. | Spec 3: Argon2id, or PBKDF2 "if Workers CPU limits bite — benchmark". Benchmark here: Argon2id ~350 ms CPU, PBKDF2-SHA256 100k ~19 ms. workerd caps PBKDF2 at 100,000 iterations, below OWASP's 600,000, so PBKDF2 is not compliant on this runtime. Argon2id needs the Workers Paid plan (30 s CPU). | Build |
| D-008 | 2026-11-10 | Contact-detail shield runs inside the ChatRoom on every message: phone numbers (including spelled-out digits and "double/triple"), emails, links, @handles and "find me on / WhatsApp me" style messages are blocked until both people are ID-verified and both have agreed to a swap. Keyword flags (money, crypto, gift cards, commercial sex, threats, under-18 signals) never block; they flag and raise risk. | Spec 1 "Verify before you meet", spec 6 pipeline, spec 8 scam flags. Blocking on flags would create false positives a moderator never sees. | Build |
| D-009 | 2026-11-10 | Editing the name or bio of a live profile sends it back to pre-moderation. Photos added later are pre-moderated one by one. | Spec 1 "Pre-moderate photos and profiles": otherwise approval could be bypassed by editing afterwards. | Build |
| D-010 | 2026-11-10 | Sexuality, gender and pronouns are one encrypted JSON field, written only while an active `special_category` consent exists, deleted when consent is withdrawn, and shown only for the parts the member ticks. Discovery never filters on undisclosed data. | Spec 1 privacy by default; spec 10 Article 9 consent. | Build |
| D-011 | 2026-11-10 | Phase 2 (creator agency) and Phase 3 (payments): no code. The `creator` and `fan` roles exist in the schema only because spec 4 lists them; nothing assigns them. | Spec 13 keeps them out of the MVP; spec 10 requires a solicitor's opinion before Phase 2. | Build |
| D-012 | 2026-11-10 | Every outside service sits behind an adapter with a development double (age, ID, image scan, email, SMS, Turnstile). The doubles refuse to run when `ENVIRONMENT` is `production`, so a missing provider fails closed. | The vendor decisions (spec 14) are open and must not block the build, and a missing vendor must never wave people through an age check. | Build |
| D-013 | 2026-11-10 | **Sample deployment on the Cloudflare Workers FREE plan**, at `platform-v0-1.hvtinnovations1.workers.dev`, deployed by Workers Builds from GitHub. | Travis: "the easiest way to get it live as a sample for free right now." The full paid-plan shape is kept in `docs/archive/wrangler.paid-plan.jsonc`. | Travis |
| D-014 | 2026-11-10 | Free plan has no Queues: background jobs run inline through the same code (`worker/lib/dispatch.ts`). With a queue bound, they are queued. | Same behaviour, weaker delivery guarantee (no retries). Fine for a sample; switch back by adding the queue bindings. | Build |
| D-015 | 2026-11-10 | Free plan: no R2 and no KV. Media is stored in a D1 table (`media_blobs`); photos are resized on the device to under 700 KB (also strips GPS data); the email-digest throttle uses the outbox table instead of KV. | Enabling R2 needs a payment card on the Cloudflare account. D1 rows are capped at 1 MB. Adding an R2 binding switches media back to R2 with no code change. | Build |
| D-016 | 2026-11-10 | Free plan: passwords use PBKDF2-SHA256 at 100,000 iterations (`PASSWORD_ALGO=pbkdf2`). Hashes are marked, so on the Paid plan members are re-hashed to Argon2id at their next sign-in. | Workers Free allows 10 ms CPU per request; Argon2id needs ~350 ms. 100,000 is below OWASP's 600,000 for PBKDF2: acceptable for a sample with no real members, not for launch (shown in the staff console as a launch blocker). | Build |
| D-017 | 2026-11-10 | **Sample mode** (`SAMPLE_MODE=1`): a SAMPLE banner on every screen; no email is sent and the link an email would carry is shown on screen, only to the device that asked (an existing account's reset link only shows on a device that account has already used); a practice page stands in for the age and ID provider; an admin can add and remove 8 labelled SAMPLE members who like back but never message; the first verified member can claim the admin seat once. | D-018 | 2026-11-10 | Staff console is inside the member app at `/admin` for the sample, not on a separate subdomain behind Cloudflare Access. Every call is checked against the staff role matrix and audited. | Spec 8 wants a separate Worker behind Access. That needs a custom domain and Access set-up: a launch task, not a sample task. The API, roles and audit are the same either way. | Build |
| D-019 | 2026-11-10 | Front end is a single-page app served as static assets, not server-rendered. | Spec 11 says "server-rendered front end". Every screen except the welcome page needs a signed-in member, so SSR adds little, and the page is noindex until launch. The SPA is also what makes the offline installable app simple. Revisit for public SEO pages at launch. | Build |

| D-021 | 2026-11-10 | If `APP_SECRET`, `INTERNAL_SECRET` or `PROVIDER_WEBHOOK_SECRET` are not set in Cloudflare, the Worker generates random values once and keeps them in D1 (`app_config`).
